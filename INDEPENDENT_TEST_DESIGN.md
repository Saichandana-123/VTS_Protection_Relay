# Independent Test Scenario Design

## Scope and status

This document is the Phase 2 design proposal only. No independent cases were
generated, no MATLAB/Simulink simulation was run, and no dataset, checkpoint,
model, evaluator, or existing report was modified.

The purpose of the next phase is to test the current six-stage model on
Simulink-generated cases that are not members of the original
`case_001`–`case_108` campaign. The current validation cases remain reserved
for validation and must not be copied into the independent set.

## Findings from the existing workflow

### Current 108-case coverage

The existing manifest contains 108 cases formed as:

- 9 scenario profiles;
- 12 protection-setting tuples;
- 13,001 samples per case at 1 ms from 0 to 13 seconds.

The nine scenario labels are:

1. `healthy`
2. `normal_load_unbalance`
3. `three_phase_vt_loss_energization`
4. `mcb_vts_operation`
5. `negative_sequence_fault`
6. `three_phase_fault`
7. `two_phase_vt_loss`
8. `three_phase_vt_loss_under_load`
9. `one_phase_vt_loss`

The existing setting values cover `VTS_STATUS` values 0, 1, and 2, both reset
modes, delays of 1, 2, 3, 5, 7, 8, and 10 seconds, and the listed current
inhibit values. However, only 12 complete combinations of these values were
used. The new design will therefore test combinations, not merely individual
values, that never occurred in the original manifest.

The current Python generator uses fixed profiles:

- `VAB` and `VBC` nominally 110 V and commonly reduced to 5 V;
- fixed baseline currents and a small set of disturbance values;
- most binary control signals held at zero;
- one disturbance window from 1 to 12 seconds.

It explicitly describes several profiles as initial proxies requiring
confirmation against the relay manual and circuit. Those profiles must not be
treated as authoritative physical scenarios without review.

### Simulink workflow

The established production-style workflow is:

1. Create input CSVs and a manifest.
2. Run `models/Simulink/run_vts_dataset.m`.
3. Load `models/Simulink/P642_VTS_Reference.slx`.
4. Simulate each input file using the 23-column matrix consisting of `time`
   plus 22 input signals.
5. Extract the three final outputs from `yout`.
6. Extract all logged detector, timer, intermediate, and SR signals from
   `logsout`.
7. Write one output CSV per case.

The older `models/Simulink/generate_vts_dataset.m` script is not suitable as
the independent generator without adaptation: it creates only four five-second
scenarios, does not use the current manifest/output schema, and saves a MAT
file. The current 108-case workflow is the relevant schema reference.

## Recommended independent test size

I recommend **48 new cases**, IDs `case_109` through `case_156`.

This size is large enough to provide 12 cases in each of four deliberately
different coverage strata while remaining feasible for 13,001-sample
Simulink runs:

| Stratum | Cases | Purpose |
|---|---:|---|
| A. Analog detector boundaries | 12 | Voltage, negative-sequence, current, and superimposed-current boundaries |
| B. Timing and transitions | 12 | Pickup, dropout, restoration, short pulses, and setting-delay transitions |
| C. Binary/control combinations | 12 | MCB, blocking, reset, pole-dead, voltage-dependent, and accelerate controls |
| D. Combined unseen operating points | 12 | Interactions between new settings, analog conditions, and binary controls |
| **Total** | **48** | 4 strata × 12 cases |

Twelve cases per stratum allow coverage across the three VTS status values and
both reset modes without claiming statistical representativeness. A smaller
set would leave important combinations untested; a full factorial design would
be unnecessarily large and would require stronger physical parameter
documentation.

## Proposed case and setting matrix

### Case IDs and naming

The independent manifest should use IDs `case_109`–`case_156`, with filenames
such as `case_109.csv` and scenario names that identify the test stratum.
These IDs must never be added to the original 108-case manifest or combined
training CSV.

The 48 cases should use **16 new setting tuples**, each used in three related
cases. Every tuple must be absent from the existing 12-tuple manifest.

The first candidate tuple set can be constructed by recombining already
observed marginal values, which avoids introducing unapproved setting ranges:

- `VTS_STATUS`: 0, 1, 2
- `VTS_RESET_MODE`: `Manual`, `Auto`
- `VTS_TIME_DELAY`: 1, 2, 3, 5, 7, 8, 10 seconds
- `VTS_I_INHIBIT`: 0.08, 0.5, 1, 2, 4, 8, 16, 32 pu
- `VTS_I2_INHIBIT`: 0.05, 0.1, 0.15, 0.2, 0.25, 0.3, 0.4, 0.5 pu

The exact 16 tuples must be generated by a manifest-level exclusion check
against all existing tuples. They must include:

- all three status modes;
- both reset modes;
- short, medium, and long delays;
- low, mid-range, and high current inhibit settings;
- low and high negative-sequence inhibit settings;
- combinations not present in the original manifest, rather than only
  permuting case order.

No value outside the documented/reference-model range should be introduced
without confirmation from the P642 manual and the Simulink model. The static
Python logic documents detector thresholds of 10/30/70/95 V, 10 V `V2`, 0.1
pu superimposed current, and 95% detector dropout relationships, but this
logic is explicitly incomplete and must not replace the Simulink reference.

### Stratum A: analog detector boundaries

For each of four selected setting tuples, create three cases:

1. Phase-voltage boundary profile:
   - nominal voltage;
   - a value just above the relevant pickup boundary;
   - a value at the boundary;
   - a value just below the dropout boundary;
   - restoration above pickup.
2. Negative-sequence boundary profile:
   - `V2` below, at, and just above pickup;
   - `I2` below, at, and just above the selected `VTS_I2_INHIBIT`;
   - a controlled return below dropout.
3. Current/superimposed-current boundary profile:
   - phase currents below and above the selected `VTS_I_INHIBIT`;
   - `delta_IA`, `delta_IB`, and `delta_IC` tested separately;
   - values below, at, and above the documented 0.1 pu superimposed-current
     boundary.

Boundary values must be obtained from the verified Simulink detector
implementation and model documentation before inputs are written. “At”
means the exact floating-point value used by the model, not an informal
approximation.

### Stratum B: timing and transitions

For four additional setting tuples, create three cases:

1. A voltage-loss pulse shorter than the selected `tVTS`.
2. A voltage-loss pulse equal to or just beyond the selected `tVTS`.
3. Repeated loss/restoration pulses that exercise timer pickup, timer reset,
   240 ms drop-off behavior, 20 ms timing, and SR state retention.

Transitions should occur at non-integer sample positions where the 1 ms grid
permits them, and also at exact sample boundaries in paired cases. Every
profile must define initial conditions, transition times, dwell times, and
restoration values in the manifest.

### Stratum C: binary/control combinations

For four additional setting tuples, create three cases:

1. MCB/VTS operation asserted during an otherwise healthy interval.
2. `VTS_BLOCKING` transitions while an analog VTS condition is present.
3. Combinations of `VTS_AUTORESET`, `VTS_MANRESET`,
   `ANY_POLE_DEAD`, `ALL_POLE_DEAD`,
   `ANY_VOLTAGE_DEPENDENT_FUNCTION`, and `ACCELERATE_IND`.

Binary signals should be changed in combinations that are accepted by the
reference model. The design must not assume that `VTS_STATUS` is equivalent to
one binary `VTS_BLOCKING` input; the existing MATLAB test comments explicitly
warn that the current binary interface does not prove distinct disabled and
indication modes.

### Stratum D: combined unseen operating points

For the final four setting tuples, create three cases combining:

1. VT loss with load and a changed negative-sequence condition.
2. A high-current fault-like condition with pole-dead or voltage-dependent
   control changes.
3. MCB/control operation during analog loss and restoration.

These are interaction tests, not claims that arbitrary independent binary
combinations are physically valid. Each combination must be reviewed against
the P642 reference model, input-port semantics, and protection-system
operating constraints before simulation.

## How the new cases differ from cases 001–108

The independent set will differ in four controlled ways:

1. **New case IDs and provenance:** cases 109–156 will be generated in a
   separate directory and will not be added to the original dataset.
2. **Unseen setting tuples:** all 16 setting tuples will be excluded from the
   original manifest.
3. **Unseen waveform values and transitions:** the existing generator mostly
   uses fixed 110 V/5 V levels, fixed current profiles, and a 1–12 second
   disturbance. The independent profiles will vary levels around verified
   detector boundaries, durations around timers, and transition sequences.
4. **Binary/control interactions:** the original generated profiles keep many
   binary controls at zero. The independent matrix will explicitly exercise
   approved control combinations and transitions.

These differences support an independent test claim only if the generated
cases are produced by the reference Simulink model and their provenance and
parameter values are retained. They do not guarantee statistical independence
or physical realism by themselves.

## Physical and logical validity gate

Before any case is generated, each proposed profile must pass this review:

1. Confirm the meaning, unit, polarity, and legal range of every nonzero
   analog and binary input in `P642_VTS_Reference.slx` and the P642
   documentation.
2. Confirm that phase relationships and voltage/current combinations represent
   a valid relay operating condition.
3. Confirm that status and reset controls are represented by the correct
   model inputs rather than inferred aliases.
4. Confirm timer delays and transition dwell times are compatible with the
   1 ms sample time and 13-second simulation window.
5. Reject any profile that is merely a convenient Boolean combination without
   a valid relay interpretation.
6. Keep an approved scenario specification and manifest row for every case.

The existing Python static logic is useful for identifying candidate boundaries
but is not sufficient as the truth source because it documents simplified,
non-time-domain behavior and includes an explicitly placeholder CT nominal
current.

## Generation and validation procedure

### Generation

The preferred Phase 3 process is:

1. Create a new input directory, for example
   `data/independent_test/inputs/`.
2. Create a separate manifest with `case_109`–`case_156`, scenario labels,
   settings, transition definitions, and generator version/hash.
3. Use a standalone generator derived from the current input schema, not the
   legacy four-scenario MAT-file script.
4. Run `models/Simulink/run_vts_dataset.m` through a separate independent-test
   wrapper or a reviewed copy configured for the independent paths.
5. Write outputs under `data/independent_test/outputs/`.
6. Never write independent files into
   `data/simulink_dataset/inputs/` or `data/simulink_dataset/outputs/`.

MATLAB/Simulink can generate the cases in principle: the checked-in
`P642_VTS_Reference.slx` and `run_vts_dataset.m` accept time-series input
matrices and extract the required outputs and logged signals. However, this
environment has not verified that MATLAB/Simulink is installed or runnable.
Phase 3 must stop and provide manual instructions if it is unavailable.

### Schema preservation

Each independent input CSV must retain:

- `time`;
- the same 22 input columns and order used by the Simulink root inports;
- 13,001 rows at 1 ms unless an approved test explicitly changes duration;
- finite numeric values;
- a separate manifest carrying `case_id`, filename, scenario, settings, and
  sample count.

Each independent output CSV must retain the existing 62-column schema:

- the input/time columns;
- `SLOW_BLOCK`, `FAST_BLOCK`, and `INDICATION`;
- the ten detector signals;
- all Stage 1–5 signals;
- timer signals;
- `SR_1_OUT` through `SR_4_OUT`;
- `case_id` and `scenario`.

Column order, signal names, sample count, and timestamp values must be checked
before any model evaluation.

### Validation gates

Every independent case must pass:

- exactly one input and one output file;
- manifest/file/case-ID consistency;
- 23 input columns before Simulink output extraction;
- 62 output columns with no missing required signal;
- 13,001 rows and time from 0 to 13 seconds at 1 ms;
- no NaN or Inf values;
- finite, binary final outputs and binary intermediate logic signals where
  applicable;
- expected numeric ranges and setting values;
- no duplicate case IDs or collision with cases 001–108;
- complete `logsout` extraction and matching sample count for every signal.

The independent-test evaluator must also reset timers and SR state at each case
boundary and record the exact checkpoint names and model version.

## Issues requiring controlled fixes before Phase 3

### 1. Checkpoint metadata inconsistencies

The current checkpoint tensors load into the current model classes, but saved
metadata is not uniform:

- `stage1_corrected_best.pt` records legacy-style input names including
  `NOT_VTS_BLOCKING`, while the current Stage 1 contract uses
  `VTS_BLOCKING` and applies the required inversion inside the model.
- `stage5_best.pt` and `stage6_best.pt` record `MCB_VTS`, while the current
  model constants use `MCB_VTS_OPTO`; the evaluator supplies an alias from
  the dataset column.
- The original `stage1_best.pt` records the older `*_OK` input contract and
  must not be used for the current integrated evaluation.

Required action before independent evaluation: do not rewrite checkpoints.
Instead, add a standalone metadata/contract validation step that verifies
tensor shapes, records the actual inference contract, and explicitly documents
the `MCB_VTS`/`MCB_VTS_OPTO` and Stage 1 blocking inversion aliases. Any
metadata normalization should be a separate approved change.

### 2. Evaluator path and case-selection issues

`evaluate_integrated_model.py` is hard-coded to the original output directory,
the saved validation case list, and a fixed result path. It cannot safely
evaluate arbitrary independent cases without a separate wrapper or controlled
parameterization.

Required action before independent evaluation:

- use a standalone independent evaluator or an approved non-default
  parameterization;
- pass an explicit independent input/output directory and case manifest;
- write results under a separate independent-test results directory;
- load `stage1_corrected_best.pt` and existing Stage 2–6 checkpoints;
- preserve `VTSStagedModel.step()` order, timers, and synchronized SR logic;
- verify that the baseline validation run still matches the saved
  post-synchronization artifact before trusting the new evaluator.

### 3. Repository-root path inconsistencies

Some training and dataset scripts resolve the repository root incorrectly when
run from their stored locations. This is especially relevant to
`train_six_stage_network.py`, `combine_simulink_dataset.py`, and
`check_dataset.py`.

Required action: do not repair these scripts as part of scenario generation.
Use explicit absolute/project-root paths or a separate independent workflow,
and verify all resolved paths before writing anything.

## Approval gate

Phase 3 should begin only after approval of:

1. the 48-case recommendation;
2. the four-stratum matrix and 16 unseen setting tuples;
3. the physical-validity review process;
4. MATLAB/Simulink availability and reference-model version;
5. the separate independent input/output/result directories;
6. the standalone evaluator and metadata-contract validation approach.

Until that approval and the physical validity review are complete, no
independent scenario should be described as valid or generated.
